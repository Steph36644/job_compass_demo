### 1.2 选型理由

#### 前端：Next.js 14 + TypeScript + Tailwind + shadcn/ui

- **Next.js**：SSR/SSG 支持，首屏性能好；App Router 的 Server Components 可减少客户端 bundle；Vercel 团队持续迭代，生态成熟。求职追踪是数据驱动型后台，部分页面可静态化（如登录、引导页），核心动态页用 CSR 即可。
- **TypeScript**：全栈类型安全，与后端共用类型定义（如枚举、DTO），降低字段不一致的 bug。
- **Tailwind + shadcn/ui**：MVP 阶段快速搭建工具型后台界面，shadcn 的组件可按需复制、可定制，比 AntD 更轻量、风格更现代。
- **Zustand**：比 Redux 轻量，适合中等规模状态；TanStack Query 负责服务端状态（投递列表、报告等），本地状态用 Zustand 管筛选条件、UI 状态。

#### 后端：NestJS + TypeScript

- **NestJS**：模块化、依赖注入、装饰器风格，适合中大型后端；与 TypeScript 前端共用类型；内置 Guards、Interceptors、Pipes，便于实现鉴权、日志、参数校验。
- **Node.js**：前后端同语言，团队技术栈统一；I/O 密集型场景（AI 调用、数据库查询）表现好。
- **为什么不选 Go/Python**：Go 性能好但 MVP 阶段开发速度不如 TS；Python AI 生态强但 Web 工程化不如 NestJS，且团队若以 TS 为主会增加维护成本。AI 调用本质是 HTTP 请求，不依赖 Python 运行时。

#### 数据库：PostgreSQL 15

- **JSONB 字段**：简历结构化数据、JD 结构化数据、AI 报告都用 JSONB 存储，灵活且支持索引查询。
- **全文搜索**：内置 ILIKE + trigram 扩展（pg_trgm）满足 MVP 搜索需求，无需提前引入 ES。
- **事务与约束**：状态流转、计数等需要事务保证一致性；外键约束保障数据完整性。
- **成熟稳定**：社区活跃，云厂商托管方案多（阿里云 RDS PostgreSQL）。

#### 缓存与 MQ：Redis + BullMQ

- **Redis**：缓存 JD 解析结果（多人投同一岗位可复用）、限流、分布式锁、会话/Token 黑名单。
- **BullMQ**：基于 Redis 的任务队列，处理 AI 报告生成（异步、可重试）、邮件发送、周复盘定时任务。MVP 阶段用 BullMQ 即可，无需引入 RabbitMQ 增加运维复杂度。

#### AI 大模型：豆包 Doubao-1.5-pro

- **合规**：国内部署需用国产大模型，避免数据出境风险；豆包由字节跳动提供，已通过国内备案。
- **中文能力**：豆包在中文 JD 解析、语义理解上表现优异，适合校招场景。
- **成本**：按需计费，Pro 版本输入约 0.8 元/百万 token，适合 MVP 阶段；可用 Lite 版本做 JD 解析（成本更低），Pro 做匹配报告与复盘。
- **兜底**：若豆包接口异常，降级到通义千问或 DeepSeek。

#### 简历解析：AI 结构化提取

- 不依赖第三方简历解析 API（如超级简历、简历解析服务），直接用大模型从 PDF 文本中提取结构化字段。
- PDF 转文本用 **pdf-parse**（纯 JS，无需系统依赖）；Word 用 **mammoth**。
- 优势：成本可控、可定制字段结构、不依赖第三方服务可用性；劣势：解析质量依赖 Prompt 优化，需人工校正兜底（PRD 已要求）。

#### 部署：Docker + Nginx + 阿里云 ECS

- **Docker Compose** 编排应用（前端、后端、PostgreSQL、Redis、Nginx），MVP 单机部署即可。
- **Nginx** 做反向代理、静态资源、HTTPS。
- 阿里云 ECS（2C4G 起步）+ RDS PostgreSQL + OSS，国内访问快、备案方便。

### 2.2 架构分层

NestJS 后端采用经典四层架构：

```
src/
├── main.ts                    # 入口
├── app.module.ts              # 根模块
├── common/                    # 通用层
│   ├── guards/                # 鉴权守卫 (JwtAuthGuard, RolesGuard)
│   ├── interceptors/          # 拦截器 (响应格式化、日志、异常)
│   ├── filters/               # 全局异常过滤器
│   ├── pipes/                 # 参数校验管道 (ValidationPipe)
│   ├── decorators/            # 自定义装饰器 (@CurrentUser)
│   └── utils/                 # 工具函数
├── config/                    # 配置
│   ├── database.config.ts
│   ├── redis.config.ts
│   └── ai.config.ts
├── modules/                   # 业务模块（按领域拆分）
│   ├── auth/                  # 认证模块
│   ├── user/                  # 用户与求职档案
│   ├── resume/                # 简历中心
│   ├── application/           # 投递建档与台账
│   ├── application-status/    # 状态机与看板
│   ├── schedule/              # 日程提醒
│   ├── ai/                    # AI 能力（JD解析、匹配报告、周复盘）
│   ├── review/                # 单岗位复盘
│   ├── insight/               # 漏斗仪表盘
│   ├── notification/          # 通知（站内/邮件）
│   └── file/                  # 文件上传（OSS）
└── shared/                    # 跨模块共享
    ├── types/                 # 共享类型定义
    ├── constants/             # 枚举、常量
    └── entities/              # TypeORM 实体
```

**分层规则**：
1. `Controller` 只处理 HTTP 层（参数接收、响应格式化），不写业务逻辑。
2. `Service` 承载业务逻辑，通过 DI 注入 Repository 和其他 Service。
3. `Repository`（TypeORM Entity + Repository 模式）只做数据访问。
4. 模块间通过 Service 接口调用，禁止跨模块直接访问 Repository。
5. AI 相关逻辑统一在 `modules/ai` 中，对外暴露服务接口，其他模块调用 AI Service。

### 2.4 模块依赖关系

```
auth ──────► user
application ─► resume, application-status, ai
schedule ───► application, notification
ai ─────────► resume, application (读取数据)
review ─────► application
insight ────► application, review, ai (调用周复盘)
notification ─► (独立，被 schedule 等调用)
```

**禁止循环依赖**：如 `application` 依赖 `ai`，`ai` 不得反向依赖 `application` 的 Service（如需数据通过 Repository 或 DTO 传入）。

### 3.3 数据存储策略

1. **大文本/结构化数据用 JSONB**：简历结构、JD 结构、AI 报告均存 JSONB，灵活且可建索引（GIN）。
2. **简历原文件存 OSS**：数据库只存 file_key，降低数据库存储压力。
3. **软删除**：users 用 deleted_at，applications/resumes 用软删除（PRD 要求可恢复），实际删除用定时任务清理 30 天前的软删除数据。
4. **归档策略**：求职结束后（用户拿 Offer 且 30 天无操作），数据标记为归档，查询时排除归档数据，提升性能。

## 四、关键技术点分析

### 4.1 JD 智能解析

#### 4.1.1 技术方案

**流程**：用户粘贴 JD 文本 → 后端接收 → 调用豆包大模型提取结构化字段 → 返回可编辑表单。

**Prompt 设计要点**：
- 明确输出 JSON Schema，约束字段与类型
- 要求保留 JD 原文引用（jd_quote），便于后续匹配报告溯源
- 区分硬性要求、职责、技能、加分项
- 指示模型"如信息缺失则返回 null，不要编造"

**关键实现**：
```typescript
// modules/ai/services/jd-parser.service.ts
async parseJd(jdText: string): Promise<ParsedJd> {
  const cacheKey = `jd_parse:${hash(jdText)}`;
  const cached = await this.redis.get(cacheKey);
  if (cached) return JSON.parse(cached);

  const result = await this.llmService.chat({
    model: 'doubao-1.5-lite',
    messages: [
      { role: 'system', content: JD_PARSE_SYSTEM_PROMPT },
      { role: 'user', content: jdText },
    ],
    response_format: { type: 'json_object' },
  });

  const parsed = this.validateAndClean(result);
  await this.redis.setex(cacheKey, 7 * 24 * 3600, JSON.stringify(parsed)); // 缓存 7 天
  return parsed;
}
```

#### 4.1.2 准确率保障

- **人工校正兜底**：解析结果进入可编辑表单，用户修改后的数据为准。
- **字段级置信度**：大模型返回每个字段的置信度，低置信度字段高亮提示用户核对。
- **Spike 验证**：上线前用 100 条真实 JD 测试，准确率 < 85% 则优化 Prompt 或更换模型。

#### 4.1.3 降级策略

1. 豆包 Lite 失败 → 切换到豆包 Pro
2. 豆包 Pro 失败 → 返回解析失败，保留 JD 原文，前端切换到手动表单
3. 链接抓取失败 → 提示用户复制 JD 文本

### 4.2 简历解析

#### 4.2.1 技术方案

**PDF**：`pdf-parse` 提取文本 → 调用大模型结构化。
**Word**：`mammoth` 提取纯文本 → 调用大模型结构化。

**为什么不用 OCR**：校招简历 99% 是文本型 PDF/Word，无需 OCR；OCR 成本高、准确率未必更好。图片型简历（少数）提示用户转 PDF。

#### 4.2.2 脱敏处理

调用 AI 前对简历文本脱敏：
- 姓名 → `[姓名]`
- 手机号 → `[手机号]`
- 邮箱 → `[邮箱]`
- 身份证号 → `[身份证号]`

脱敏映射表存 Redis（短期），AI 返回后不还原（结构化数据中也不保留 PII，展示时从原文取）。

### 4.3 JD×简历 AI 匹配报告

#### 4.3.1 技术方案

**输入**：结构化 JD + 结构化简历 + 求职档案。
**输出**：match_reports 表定义的结构。

**核心 Prompt 逻辑**：
1. 逐条读取 JD 要求（硬性/职责/技能/加分）
2. 对每条要求，在简历中搜索匹配证据
3. 判定 matched / partial / missing
4. 对 missing/partial 项生成行动建议
5. 汇总缺口，生成简历优化建议

**要求模型**：
- 必须引用 JD 原文片段（jd_quote）和简历原文片段（resume_quote）
- 行动建议分类型（补项目/学技能/优化表述/调方向）
- 不编造经历、不编造数据

#### 4.3.2 防幻觉机制（工程层）

1. **引用校验**：后端校验返回的 jd_quote 和 resume_quote 是否真实存在于输入文本中（子串匹配），不存在则丢弃该条或标记为不可信。
2. **建议模板化**：行动建议通过模板生成（如"该岗位要求『{skill}』，你的简历中未体现，建议..."），降低模型自由发挥。
3. **分数计算独立**：匹配度分数用规则引擎计算（匹配项数/总项数加权），不完全依赖模型打分，避免分数虚高。
4. **用户反馈**：每条判定可点"不准确"，记录到 feedback 表，用于后续 Prompt 优化和人工抽检。

#### 4.3.3 异步生成

- 匹配报告生成可能 10–30 秒，用 BullMQ 异步处理。
- 前端轮询或 WebSocket 推送生成状态。
- 生成失败时保留上次成功报告，前端提示重试。

### 4.4 状态机实现

#### 4.4.1 状态枚举与流转

```typescript
// shared/constants/application-status.ts
export enum ApplicationStatus {
  PENDING = 1,      // 待投递
  APPLIED = 2,      // 已投递
  ASSESSMENT = 3,   // 测评/笔试
  INTERVIEW = 4,    // 面试中
  OFFER = 5,        // Offer
  REJECTED = 6,     // 已被拒
  CLOSED = 7,       // 已终止
}
```

#### 4.4.2 状态机 Service

```typescript
// modules/application-status/services/status-machine.service.ts
@Injectable()
export class StatusMachineService {
  // 允许的流转（任意状态可到任意状态，由业务规则约束）
  async transition(
    applicationId: number,
    toStatus: ApplicationStatus,
    remark?: string,
  ): Promise<void> {
    await this.dataSource.transaction(async (manager) => {
      const app = await manager.findOne(Application, {
        where: { id: applicationId },
        lock: { mode: 'pessimistic_write' },
      });
      const fromStatus = app.status;

      app.status = toStatus;
      app.updatedAt = new Date();
      await manager.save(app);

      await manager.save(StatusLog, {
        applicationId,
        fromStatus,
        toStatus,
        remark,
      });
    });
  }
}
```

**设计决策**：MVP 阶段不限制状态流转方向（允许跳级、回退、终态激活），因为校招流程多变（如流程重启、HR 重新联系）。只做数据一致性保障（事务 + 行锁）。

### 4.5 日程提醒调度

#### 4.5.1 技术方案

用 **BullMQ** + **node-cron** 实现：

1. **node-cron** 每分钟触发扫描任务：查询 `schedules` 表中 `scheduled_at` 在未来 24h+2h 内且未发送提醒的记录。
2. 判断是否满足提醒条件（提前 24h / 提前 2h），满足则：
   - 插入 `notifications` 表（站内通知）
   - 若用户邮箱已验证，调用邮件服务发送
   - 标记 `notified_24h` / `notified_2h` 为 true
3. **投递跟进提醒**：每天凌晨扫描状态为"已投递"且 `apply_date` 距今 7 天的记录，发送跟进提醒。

```typescript
// modules/schedule/services/reminder.service.ts
@Cron('0 * * * *') // 每分钟
async scanSchedules() {
  const now = new Date();
  const in24h = new Date(now.getTime() + 24 * 3600 * 1000);
  const in2h = new Date(now.getTime() + 2 * 3600 * 1000);

  const schedules = await this.scheduleRepo
    .createQueryBuilder('s')
    .where('s.scheduled_at <= :in24h', { in24h })
    .andWhere('s.scheduled_at > :now', { now })
    .getMany();

  for (const s of schedules) {
    if (!s.notified24h && s.scheduledAt <= in24h) {
      await this.sendReminder(s, '24h');
      s.notified24h = true;
    }
    if (!s.notified2h && s.scheduledAt <= in2h) {
      await this.sendReminder(s, '2h');
      s.notified2h = true;
    }
    await this.scheduleRepo.save(s);
  }
}
```

#### 4.5.2 幂等性

- `notified_24h` / `notified_2h` 字段保证不会重复发送。
- 邮件发送失败标记 `email_sent = false`，可重试。

### 4.6 AI 周度复盘

#### 4.6.1 技术方案

1. **node-cron** 每周一凌晨 2 点触发：查询所有活跃用户上周（周一至周日）的投递与状态变更。
2. 对有数据的用户，汇总：
   - 漏斗数据（各状态数量、转化率）
   - 被拒原因聚合
   - 各方向/渠道/简历版本回复率
3. 调用大模型生成诊断与建议（输入为汇总数据，非原始数据，降低 token 消耗）。
4. 存入 `weekly_reports` 表，生成站内通知。

#### 4.6.2 数据计算

- 转化率用 SQL 聚合查询，避免应用层循环。
- 回复率 = (测评+面试+Offer) / 已投递数。
- 瓶颈判断用规则（笔试率<10% → 初筛问题），不完全依赖 AI，保证结论有数据支撑。

### 4.7 认证与安全

#### 4.7.1 JWT 认证

- **Access Token**：有效期 2 小时，存前端内存/HttpOnly Cookie。
- **Refresh Token**：有效期 7 天，存 HttpOnly Cookie + 数据库（可撤销）。
- 刷新接口校验 refresh token 并轮换。
- 注销/退出时将 token 加入 Redis 黑名单。

#### 4.7.2 数据安全

- **传输加密**：全站 HTTPS。
- **存储加密**：JD 原文、简历 structured_data 中的敏感字段用 AES-256-GCM 加密，密钥存 KMS/环境变量。
- **AI 调用脱敏**：见 4.2.2。
- **SQL 注入**：TypeORM 参数化查询，禁止拼接 SQL。
- **XSS**：前端对用户输入（JD 原文、备注）做转义渲染，不使用 v-html/dangerouslySetInnerHTML 渲染未净化内容。
- **CSRF**：SameSite Cookie + CSRF Token。
- **限流**：Nginx 层 + NestJS `@nestjs/throttler`，登录接口 1 分钟 5 次，AI 解析接口按用户限频。

### 4.8 文件上传（OSS）

- 简历文件上传走后端签名直传 OSS（STS 临时凭证），不经过后端服务器，降低带宽压力。
- 上传前校验类型（PDF/DOCX）和大小（≤10MB）。
- 上传后触发解析任务（BullMQ）。

## 九、技术债务与后续优化

1. **搜索引擎**：MVP 用 PostgreSQL ILIKE，数据量增长后（>10 万条投递）引入 Meilisearch。
2. **MQ**：MVP 用 BullMQ，任务类型增多后迁移到 RabbitMQ。
3. **微服务拆分**：MVP 单体 NestJS，AI 模块可独立拆分为服务（Python/Go），通过 gRPC 通信。
4. **多租户**：当前单租户（个人用户），B 端需求出现时引入租户隔离。
5. **CDN**：静态资源与简历文件可走 CDN 加速。
